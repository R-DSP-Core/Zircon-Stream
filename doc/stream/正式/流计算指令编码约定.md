# 流计算指令编码约定

本文记录当前 Stream Engine 自定义指令中 `rd/rs1/rs2` 三个字段的语义。核心约定是：

> 一个字段是否表示 stream ID，由指令类型和该操作数的角色决定，不能仅根据字段位置判断。

## 1. 基本格式

所有流指令使用 RISC-V `CUSTOM_0` opcode：

```text
31          25 24       20 19       15 14    12 11         7 6          0
+--------------+-----------+-----------+--------+------------+------------+
|    funct7    |    rs2    |    rs1    | funct3 |     rd     |    0x0b    |
+--------------+-----------+-----------+--------+------------+------------+
```

当前共有 6 个物理 stream buffer，因此 stream ID 的有效范围为 `0..5`，硬件取寄存器字段的低 3 bit 作为直接编码的 stream ID。

直接编码的 stream ID 必须是编译期数字字面量或数字宏。例如：

```c
#define X_FIFO 4
cal_stream_mul(0, 0, X_FIFO);
```

不能把运行时 C 变量传给 `cal_stream_mul` 等直接编码宏。配置指令不受此限制，其参数仍通过 GPR 传递。

## 2. 字段角色

| 类型 | 软件接口 | `rd` | `rs1` | `rs2` | GPR 依赖 |
| --- | --- | --- | --- | --- | --- |
| CFG | `cfg_*` | `x0` | 配置值所在 GPR | fifo/维度参数所在 GPR | 读取 `rs1/rs2`，`cfg_reuse_empty` 除外 |
| SSS | `cal_stream_add/sub/mul` | 目的 stream ID | 源 stream ID 0 | 源 stream ID 1 | 无 |
| SSR | `cal_stream_rd_add/sub/mul` | 目的 GPR | 源 stream ID 0 | 源 stream ID 1 | 只写 `rd` |
| SSP | `cal_stream_pp` | 非 GPR 字段；当前 PP 目的由硬件映射 | 源 stream ID 0 | 源 stream ID 1 | 无 |
| RRS | `cal_rjrk_stream_pp` | `x0` | 标量源 GPR 0 | 标量源 GPR 1 | 读取 `rs1/rs2` |

字母含义：`S` 表示 stream buffer，`R` 表示通用寄存器，`P` 表示 ping-pong buffer 写回路径。

### 2.1 CFG

CFG 指令中的 `rs1/rs2` 是真正的 GPR 编号。Stream Engine 读取寄存器值后，再从值中取得配置内容和 fifo ID。例如 `cfg_i_limit(limit, fifo_id)` 中：

```text
RF[rs1] = limit
RF[rs2] = fifo_id
```

因此 CFG 参数可以是运行时变量，不能把 CFG 的寄存器字段直接解释成 stream ID。

### 2.2 SSS

SSS 的三个操作数全是 stream，因此三个寄存器形状的字段都直接保存 stream ID：

```text
rd  = dst stream ID
rs1 = src0 stream ID
rs2 = src1 stream ID
```

这些字段不读取或写入 GPR，也不参与 rename、RAW/WAW 依赖判断。

### 2.3 SSR

SSR 从两个 stream 读取数据，并把结果写回一个真正的通用寄存器：

```text
rd  = compiler-allocated GPR destination
rs1 = src0 stream ID
rs2 = src1 stream ID
```

因此 `rd` 必须参与寄存器重命名和写回，不能硬编码成 stream ID；`rs1/rs2` 则不产生 GPR 读取依赖。

### 2.4 SSP 与 RRS

`cal_stream_pp` 从两个 stream 读取，结果走 Even PP 写回路径。`funct7=1` 用于选择 PP 指令子类型，不是 ALU 运算码；当前算术操作仍为加法。

`cal_rjrk_stream_pp` 的两个源操作数是实际标量数据，因此 `rs1/rs2` 必须读取 GPR，并参与正常的寄存器依赖判断。结果走 Odd PP 写回路径。

## 3. 算子编码

| 类型 | `funct3` | `funct7` | 运算/用途 |
| --- | ---: | ---: | --- |
| SSS | 2 | 0 | add |
| SSS | 2 | 8 | sub |
| SSS | 2 | 16 | mul |
| SSP | 2 | 1 | stream add 后写 PP |
| RRS | 6 | 0 | 当前为 GPR or 后写 PP |
| SSR | 7 | 0 | add，结果写 GPR |
| SSR | 7 | 8 | sub，结果写 GPR |
| SSR | 7 | 16 | mul，结果写 GPR |

其中 SSS/SSR 的 `funct7` 才承载 add/sub/mul 运算选择。SSP 的 `funct7=1` 只用于识别 PP 路径。

## 4. 硬件解码约束

`Decoder.scala` 先提取三个字段中的 stream ID 候选值，再根据 `useBuffer` 对每个字段独立有效化：

```text
useBuffer(i) = true  -> fifoId(i) 为指令字段中的直接 stream ID
useBuffer(i) = false -> fifoId(i) 清零，不允许用于索引 stream buffer
```

这保证了：

1. SSS 的三个字段都能选择 stream。
2. SSR 的 `rd` 只作为 GPR destination，不会被误用于索引 FIFO。
3. RRS/CFG 的 `rs1/rs2` 仍走寄存器数据通路。
4. 非 stream 字段即使编码值大于物理 FIFO 数量，也不会形成无效 FIFO 访问。

`PreDecoder.scala` 必须保持相同分类：SSR 置 `rdVld`，RRS/CFG 置 `rjVld/rkVld`，SSS/SSP 的直接 stream ID 字段不产生 GPR 依赖。

## 5. FIFO 角色与索引

当前 FIFO 分工如下：

| FIFO | 角色 |
| ---: | --- |
| 0 | 普通源流 0；复数模平方中的 `re` |
| 1 | 普通源流 1；复数模平方中的 `im` |
| 2 | 普通 store stream |
| 3 | Layout Transform buffer |
| 4 | 计算中间流 X；`re * re` |
| 5 | 计算中间流 Y；`im * im` |

只有 X/Y 需要两套相互独立的索引：

```text
specI / archI
    X/Y 作为源操作数时使用的消费索引

specComputeWriteI / archComputeWriteI
    SSS 向 X/Y 写结果时使用的生产索引
```

FIFO 0/1/2/3 继续沿用原有单套索引，不增加计算生产索引。

当一条指令的两个源 ID 相同时，例如 `cal_stream_mul(0, 0, 4)`，两个 ALU/MDU 输入读取同一个 FIFO 元素，但对应流的消费索引和 ready 计数只推进一次。

## 6. 复数模平方示例

```c
cal_stream_mul(0, 0, 4);       // SSS: X = re * re
cal_stream_mul(1, 1, 5);       // SSS: Y = im * im
acc += cal_stream_rd_add(4, 5); // SSR: GPR acc += X + Y
```

前两条指令分别使用 X/Y 的生产索引。第三条指令使用 X/Y 的消费索引，并将结果写入编译器分配的 GPR。

前两条指令的固定编码分别为：

```text
cal_stream_mul(0, 0, 4) -> 0x2000220b
cal_stream_mul(1, 1, 5) -> 0x2010a28b
```

SSR 指令的 `rd` 由编译器分配，因此完整 32 bit 指令字不是固定值，但其 `rs1=4`、`rs2=5`、`funct3=7`、`funct7=0` 保持不变。

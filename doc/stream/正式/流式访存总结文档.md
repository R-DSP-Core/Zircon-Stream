#  Stream Engine 工作机制说明

##  1. Stream Engine 基本结构


### 1.1 iCntMap（迭代计数器）

在流式计算中（如向量加 a[i] + b[i] → c[i]），每次执行一条 CALSTREAM（流计算指令）时，硬件必须知道：

> **这一条计算指令要使用 Buffer 中的第几个元素？**

由于在流式计算中，操作数索引一般都会按某种规律变化，所以流计算指令的指令码本身不必携带 **各个流操作数 在相应流Buffer中的索引**，各操作数的索引 是指令来到流水线时动态获取的

> 编码时，假若把操作数索引编址在指令码中，则RF级需要先从通用寄存器中读出操作数索引，再利用该索引从流Buffer中取数，这会影响主频

例如：

* 第一次计算 → 使用 Buffer[0]
* 第二次计算 → 使用 Buffer[1]
* ……以此类推

为了实现这一点，每条流都对应一个迭代计数器，统一存放在 `iCntMap` 里

我们需要维护的逻辑是：

1. 计数器何时变化
2. 计数器按何种方式变化
3. 多发射的每条流计算指令如何根据计数器获取属于自己的操作数索引


---

### 1.2 stream Buffer（每个 stream 一个）

每个 **stream 流** 分配：

* 一个 Buffer，包含 **X 项**
* 每项是 **4B word**
* 每项配套一个 flag，称为 **消费计数**


其中：

```java
X = 2 × L2CacheLine_WORD
```

即：每个流buffer是一个 有两个 cacheline 规模的双缓冲结构，分为两个半区

---

### 1.3 readyMap

项的个数和Buffer项的个数一样，每一项为若干bit

| 流类型         | ready > 0 ( = x )             | ready = 0           |
| ----------- | --------------------- | ------------------- |
| **Load 流**  | 数据已经填充到 FIFO，可被计算指令消费`x`次 | 空闲，可从主存读取数据填充到 FIFO |
| **Store 流** | FIFO 中有计算结果，准备写回主存    | FIFO 空闲，计算单元可写入新结果  |


---

### 1.4 配置表

每个流（Stream）在使用前需要配置完整的访存与索引更新信息。整体上，这些配置可分为 **访存相关信息** 和 **索引更新相关信息** 两大类。

#### 1.4.1 访存相关信息

该类配置用于描述流在主存中的数据布局以及访存方式，决定 **数据从哪里来、以什么步长取、如何复用**。

##### 基本约定（统一抽象）

对于任意一个流，其数据访问层次结构统一抽象为：

> **流（Stream） → Block → Tile → Word**

* 每个 **流** 由若干个 **Block** 组成（**每个Block中的数据一致**）
* 每个 **Block** 由若干个 **Tile** 组成
* 每个 **Tile** 由若干个 **Word** 组成

需要配置的信息如下：

* **addrCfg**
  每个流在主存中的起始地址（Base Address）。

* **outerIterMap**
  每个流对应的 **Block 数量**

* **lengthMap**
  每个 Block 对应的 **Tile 数量**

* **tilestride**
  相邻 **Tile** 首地址之间的步长

* **stride**
  相邻 **Word** 之间的地址步长

* **reuseMap**
  描述每个 **Word** 被消费（使用）的次数，用于支持数据复用

> 通过上述配置，流引擎可以在 Block / Tile / Word 多个层次上，精确地生成访存地址并完成高效的数据获取。

---

#### 1.4.2 索引更新相关信息

该类配置用于描述 **索引计数器（icntMap）** 的更新规律，从而控制流中数据的访问顺序。

对于普通的流操作数索引，硬件中维护的是一组动态状态：

* `iCnt`：当前索引
* `iLimit`：当前这一段递增区间的上界
* `iRepeat`：当前区间已经重复了多少次

对应的静态配置是：

* `iLimitCfg`
* `iRepeatCfg`

它们共同描述如下这类模式：

```text
[0, limit)                     重复 repeat 次
[limit, 2×limit)              重复 repeat 次
[2×limit, 3×limit)            重复 repeat 次
...
```

也就是说：

* 索引总是在一个长度固定的区间内递增
* 当本区间递增到上界后，若重复次数还未用完，则回到该区间起点继续
* 当重复次数用完后，不再回到本区间，而是进入下一个区间

这一抽象既可以描述向量加中的简单线性递增，也可以描述矩阵乘中“某一段反复扫描若干次再进入下一段”的访问模式。

在 `Stream.scala` 中，dispatch 路径和 commit 路径各自维护了一份索引状态：

* `specI`：推测态，在 dispatch 时分配索引
* `archI`：架构态，在 commit 时更新，用于分支预测失误后的恢复

这样可以保证流计算指令在乱序机器中既能提前获得索引，又能在 flush 时恢复到正确状态。

##### 普通索引更新配置项

* **`cfg_i`**
  配置某个流的软件视角总迭代规模。当前实现里 `length` 和 `outerIter` 主要用于访存侧的 block / tile 控制。

* **`cfg_i_limit`**
  配置每个递增区间的长度。若设为一个足够大的值，则该流表现为简单线性递增。

* **`cfg_i_repeat`**
  配置每个递增区间需要重复的次数。

##### FFT-32 的 PP 写回索引

FFT-32 与前面的向量加、矩阵乘还有一个关键区别：部分流计算指令的结果并不是写到独立的 store stream，而是写回 **两个 load stream buffer 的另一条 line**。这对应硬件中的 PP（ping-pong / parity-pattern）写回路径。

为此，除了普通 `iCntMap` 之外，硬件还额外维护了两组目的索引状态：

* `specPP / archPP`
* `ppBaseCfg`
* `stageLimitCfg`

其中：

* `CALSTREAMPP` 对应 Even PP 写回路径
* `CALRJRKSTREAMPP` 对应 Odd PP 写回路径

PP 路径的索引不是简单的“线性递增 + 回环”，而是要跟随 Stockham FFT 每个 stage 的蝶形输出位置变化。`updatePPState()` 会根据：

* 当前 stage
* 当前 stride
* 当前 stage 内 limit
* 当前 block 的 base

生成本条指令写回到哪个 stream buffer、哪一条 line、哪一个 word。

它的本质是：前几级 FFT 的输出始终写到当前 block 中“另一条 line”，这样当前 line 在被消费完之后就能尽快腾空，供下一 block 异步取数使用。TODO

### V2：流Engine 连 L2-Cache & AXI

- 动机：
  1. 顺序流不需要Cache作为缓存，应直接向AXI发送请求
  2. 需要Cache缓存的流，需缓存的数据没必要来到L1，因此直连L2

- 与L2的连接
  1. SE与L2以流水的方式连接，SE仍然是维护四级流水，L2部分复用了部分channel2的数据通路
  2. SE的请求与L1-D的请求在L2的C2S1会有一个竞争的关系，目前出于实现难度的考虑，允许L1的请求优先通过
  3. L2给L1-D的接口中读数据是一整个l1-cacheline，而给SE的读数据是一个word，当L2 hit时，数据能够以流水的形式每cycle给SE返回一个数据

- 与AXI的连接
  > 参考V0部分的介绍，基本没有改动

- 配置问题：通过简单的指令即可配置某个load流是向L2 还是向AXI发送请求

**Store流仍然直连AXI**

### V1：流Engine 只连 L1-Cache（动机见“矩阵乘的流”部分）

Stream Engine不再通过AXI向主存发送访存请求，而是直接向Cache发送请求。Stream Engine内部维护一个类似访存流水线的4级流水：

#### 访存请求发送（RF级）
在RF级发送访存请求（会**阻塞**访存流水线 RF级的请求）。先前通过AXI访存的粒度是流Buffer一个半区的长度，而从L1Cache访存的粒度是**单字**，所以需要维护一个循环计数器loadWordCnt记录向L1Cache发送了多少个访存请求，地址由基地址和计数器共同决定：

```scala
loadAddr = addrDyn(loadFifoIdReg) + loadWordCnt * strideCfg(loadFifoIdReg)
// addrDyn是该流当前tile取数首地址
// strideCfg是该流各Word取数间隔
```

当loadWordCnt达到半区长度时，这一轮的所有访存请求已经全部发送，将访存请求拉低，并根据`tileStrideCfg`更新`addrDyn`寄存器

#### 访存请求处理（D1/D2级）
对应流水线中的D1/D2 Stage，逐级流水访存请求、访存地址、写Buffer的地址等信息用于WB级。同样与访存流水线一致，在D1级给L1Cache提供用于mmu的地址（bug）。
```
io.dc.rreqD1      := loadValidRegD1
io.dc.paddrD1     := loadAddrRegD1
```
#### 访存数据写回（WB级）
前面流水级在发送Cache miss堵塞时，需要保持原值，但是对于D2到WB级的更新，当发生Cache miss请求时，该级的所有信号(包括写使能信号)应该清空：
```
val loadWordCntRegWB = WireDefault(ShiftRegister(
   Mux(io.dc.miss || io.dc.sbFull, 0.U, loadWordCntRegD2),
   1,
   0.U((l2Offset-2).W),
   true.B
))
```
写使能、写地址由前面的流水级传递下来，写数据由cache提供，并根据reuseCfg在readyMap中置相应的消费数


**Store流仍然直连AXI**

### V0：流Engine 只连 AXI（原始版本）

#### Load 流：从主存读数据到 Buffer

**粒度：**
* 一次从AXI请求一个L2 Cacheline，对应双缓冲结构中的一个半区

**条件与限制：**

* 为了实现简便，取数一个条件是 Buffer某个半区的所有项 ready = 0（空闲）
* 取数的另一个条件是该流的burst次数未超过其配置次数
* 各流按半区0->半区1->半区0->半区1这样的方式取数，并且半区0取第0、2、4、6...组cacheline数据，半区0取第1、3、5、7...组cacheline数据

**过程：**

1. **select stream**
   从 Buffer 空闲、配置完毕的流中选择一个读主存。
2. **AXI 读请求**
   直连 AXI Arbiter，与 L2 竞争带宽。
3. **写入 Buffer：**
   依次写入要填入的半区：
4. 写完数据 有如下副作用
   1. `ready = 1`
   2. burstCnt递增
   3. addrCfg递增（当前仅实现线性流）



#### Store 流：Buffer → 主存

**条件：**

* store Buffer 某个半区 所有index  `ready = 1`

**过程：**

1. **判断是否可写**
2. **AXI 写入主存**
3. 写回主存有如下副作用 
   1. `ready = 0`
   2. burstCnt递增
   3. addrCfg递增（当前仅实现线性流）


## 3. CALSTREAM 指令在流水线中的流动（Dispatch -> Issue -> Execute -> Writeback）

CALSTREAM（流计算指令）会从Buffer中读数，计算，写回，完成一次元素级计算

为了保证正确的数据依赖与吞吐，硬件对 CALSTREAM 做了完整的流水处理：


### **3.1 Dispatch 阶段：为流计算指令分配 index**

#### **① 获取当前这条指令对应的 index**

因为流计算指令在 issue 级需要依据 index 判断是否可以发射，因此 index 必须在 issue 之前生成，这里选择在 dispatch 级获取。

Stream Engine 会根据配置好的规则更新各个流的推测态索引状态，并为一个 dispatch 宽度内的流计算指令分配正确的 `iterCnt`。

例如，假设当前icntMap中该流操作数对应的计数器值是31，根据配置可知下一个更新值是0。而dispatch宽度是3，并且第1条和第3条指令都是流计算指令，那么他们的index值分别应该是31(%64)和0(%64):

```
index = iterCnt % Buffer_Depth
```

#### **② iCntMap更新**

普通 `CALSTREAM / CALSTREAMRD` 在 dispatch 获取 index 时，会对 `specI` 产生副作用。dispatch 级有多少条流计算指令下一周期真正离开该级（fire），对应流的计数器就要前进多少，并根据 `iLimitCfg / iRepeatCfg` 判定是否回环：

FFT-32 中新增的 `CALSTREAMPP / CALRJRKSTREAMPP` 则不同。它们的源操作数索引仍由 `specI` 提供，但目的写回索引改由 `specPP` 提供。对应实现位于：

* `Dispatch.scala`
* `Decoder.scala`
* `Stream.scala` 中的 `updateIState()` 与 `updatePPState()`

在 `Dispatch.scala` 中，目的操作数共有三种来源：

* 普通 store buffer 写回：`fireStreamOp(2)`
* Even PP 写回：`fireStreamOpPP(Even)`
* Odd PP 写回：`fireStreamOpPP(Odd)`

dispatch 会根据指令类型为目的操作数选择正确的索引生成器，而不是再把所有写回都视为同一种线性递增模式。

此外，当前实现已经维护了：

* `specI / archI`
* `specPP / archPP`

配合 commit 侧传回的 `fireStreamOp`、`fireStreamOpPP` 与 `iterCnt`，在 flush 时恢复推测态，因此这里的“分支预测失误恢复”已经纳入实现。


### **3.2 Issue 阶段：检查 Buffer 是否就绪（指令能不能发射？）**

Issue 阶段决定该 CALSTREAM 指令是否可以真正进入执行单元。

对于每个计算指令（例如 `a[i] + b[i] -> c[i]`），Issue 必须检查：

* **Load 流的 Buffer 对应 index 的 ready > 0（有数据可消费）**
* **若需要写普通 store Buffer，检查对应 index 的 ready == 0（有空位可写）**
* **若需要写 PP Buffer，检查被映射到的那一个 load buffer line位置当前 ready == 0**

示例（向量加）：

| 流 | 类型    | 条件                  |
| - | ----- | ------------------- |
| A | Load  | readyMap(0)[i] > 0 |
| B | Load  | readyMap(1)[i] > 0 |
| C | Store | readyMap(2)[i] == 0 |


普通向量加只涉及前三个条件；FFT-32 的 `CALSTREAMPP / CALRJRKSTREAMPP` 还会额外检查 PP 写回位置是否已经腾空。对应逻辑位于 `Stream.scala` 的 issue 判断中：

```scala
val (ppId, ppIdx) = getPP(io.iss(i).iterCnt(2), ppDecBase)
val ppRdy = !io.iss(i).usePPBuffer || loadreadyMap(ppId)(ppIdx) === 0.U
```

只有相关条件都满足，这条指令才允许发射。


### **3.3 Execute 阶段：读取 → 计算 → 写回**

Execute 包含三个流水级，与普通整数指令风格保持一致：


#### **3.3.1 ReadOp（操作数读取）**

流计算指令有特殊的 opcode。对于需要从流中读取源操作数的指令，ReadOp 级会根据 dispatch 时分配好的 `iterCnt` 从 Buffer 中取出本次计算需要的操作数：

```
rdata1 = Buffer(A)[index]
rdata2 = Buffer(B)[index]
```

这里又分两类：

* `CALSTREAM / CALSTREAMRD / CALSTREAMPP` 需要从流 buffer 读取源操作数
* `CALRJRKSTREAMPP` 的源操作数来自通用寄存器，不占用流源操作数读口

因此新版本在解码后增加了 `needStreamSrc` 信号，避免把所有流计算指令都错误地当作“必须读两个流源操作数”处理。

### **3.3.2 ALU 计算**

当前硬件已经不再只有一种流计算形式，而是分成了三类：

* `CALSTREAM`：流流流，结果写普通 store stream
* `CALSTREAMRD`：流流寄，结果写通用寄存器
* `CALSTREAMPP / CALRJRKSTREAMPP`：结果写回 PP buffer

其中 `CALSTREAMRD` 目前已经支持不同 `funct7` 区分不同算子，例如 FFT-32 中会用到“流加得到寄存器结果”和“流减得到寄存器结果”两类形式。


#### **3.3.3 Writeback（写入 store Buffer / 通用寄存器）**

若向普通 store Buffer 中写入，需要同时更改对应 index 的 flag：

```
Buffer(C)[index] = result
readyMap(C)[index] = 1
readyMap(A)[index]--
readyMap(B)[index]--
```

若是 `CALSTREAMPP / CALRJRKSTREAMPP`，则写回目的地不再是 `Fifo(2)`，而是通过 `getPP()` 将 `iterCnt(2)` 翻译成：

* 写回哪个 load buffer line
* 写回该 buffer 中哪一个位置

然后把结果直接写回该位置，并把 `readyMap` 重新置成 `reuseCfg(ppId)`，表示该位置已经成为下一阶段可继续被消费的新数据。

这一步完成后：

* load 流消费数减少，归0时可被下一轮访存填充
* 普通 store 流对应 index 变为 ready，可被 AXI 写回主存
* PP 写回位置对应的 load 流位置重新变为 ready，可被后续 FFT stage 继续消费

### **3.4 Commit 与 Flush：保证索引状态可恢复**

由于流索引在 dispatch 阶段就已经带副作用地向前推进，如果只维护一份状态，那么一旦分支预测失误或异常 flush，就会出现“指令被清掉了，但索引已经前进”的问题。

当前实现采用两套状态：

* dispatch 更新 `specI / specPP`
* commit 更新 `archI / archPP`

当 commit 发出 flush 时，Stream Engine 直接用架构态覆盖推测态，并同时恢复 `archLoadReadyMap`。这样普通索引和 FFT-32 的 PP 索引都能回到正确位置。


## 4. 向量加（Vector Add）执行示例

**该示例是基于之前的版本讲述，可能与目前版本实现稍有不符**

下面以三个流（a、b、c）说明 512 elements vector add：

```
c[i] = a[i] + b[i]
```


### 4.1 Buffer 分配

每个流分配：

* 一个pingpong buffer（两个半区）：`line0` 和 `line1`
* 每个半区含 一个l2 cacheline（32 个 word）
* 每 word 搭配 1bit ready 标志


双缓冲结构保证计算与访存可完全重叠。


### 4.2 执行步骤

#### (a) 指令配置

配置：

* a, b 的起始地址
* 每次取 32 word
* 共需 512 word → 16 次 burst

---

#### (b) 第一批取数：填 line0

AXI 依次取：

```
a[0..31] → a.line0
b[0..31] → b.line0
```

ready 置 1。

---

#### (c) 第一轮计算（0–31）+ 第二批取数（32–63）

计算单元开始：

```
c[i] = a[i] + b[i],  i = 0..31
```
算好后load流相应line0中的ready位会拉低，store流的会拉高

同时 AXI 获取下一批：

```
a[32..63] → line1
b[32..63] → line1
```

---

#### (d) 第二轮计算（32–63）+ 第三批取数（64–95）

第二轮计算开始：

```
c[i] = a[i] + b[i], i = 32..63
```

准备从主存获取下一批（64–95）到 line0。


由于line1已经取好，并且计算速度(line0的消费速度)快于访存(line1的取数速度)，因此两个load流的line0肯定已经被拉低，所以可以取数


```
a[32..63] → line0
b[32..63] → line0
```

---

#### (e) 第 n 轮循环

双缓冲循环往复：

```
计算本批（i）
访存下一批（i+1）
```

直到 16 轮完成所有 512 word 计算。



### 4.3 执行效果

* AXI 访存几乎无空闲
* 计算完全被访存隐藏
* 每轮延迟 ≈ 两次 32-word 读的耗时
* 增大 burst size 可进一步减少握手带宽损耗

最终实际测量：

```
≈ 1700–1800 cycle 完成整段 vector add
```

## 5 矩阵乘的流

上述向量加的例子中，数据不存在复用（每个元素取回后只访问1次），也不存在复杂的访存pattern（顺序取数）
但在矩阵乘中会存在，下面首先简单描述下矩阵内积乘算法(MNK)：

* 计算C11：由A的**第一行**和B的第**一**列计算得到
* 计算C12：由A的**第一行**和B的第**二**列得到
* ...
* 计算C21：由A的**第二行**和B的第**一**列得到
* 计算C22：由A的**第一行**和B的第**二**列得到
* ...

我们的设计是，将A的一行和B的一列取到流buffer中，使用**流乘法指令**和**普通加法指令**进行乘累加操作，C的结果写回通用寄存器

为了实现上述算法，需要实现：
1. 流 Engine 按列取数据：数据按列组织在流Buffer中，以便流计算指令能够高效索引数据。
2. 流 Engine 与 Cache 的接口：使用Cache作为流Buffer的后备缓存，节省内存带宽
3. 流 Buffer 的复用：对于某些流，不能像原来一样使用一次之后就无效Buffer数据
4. 特殊的 icntMap 更新逻辑：原有的icntMap只需要递增，现在需要一些回环-重复的模式

### 5.1 矩阵A内存取数：Stream Buffer复用
我们采用最常见的内积算法，矩阵A的一行被读入到Stream buffer后，各 element 应该被消耗掉N次，这一功能需要有新增的指令来配置：
```
static int cfg_reuse(uint32_t reuse,int fifo_id)
{
    asm volatile (
       ".insn r 0x0b, 4, 0, x0, %0, %1"
             :
             :"r"(reuse),"r"(fifo_id)
     );
    return 0; 
}
```
该指令配置数据被读入到Stream Buffer中后被使用的次数，因此数据读入到Stream Buffer时，readymap被初始化为配置的次数：
```
readyMap(A)[index] = reuseCfg(A)
```
每当流计算指令消耗掉一次index位置的数据：
```
readyMap(A)[index] = readyMap(A)[index] - 1
```
直到为0，表示该数据不会再被复用，Stream Buffer中的位置空闲，流Enigne 控制逻辑可以为该Buffer发起向主存的一次新请求


### 5.2 矩阵B内存取数（Cache复用）

与矩阵A的复用不同，矩阵B的一列被读入Stream Buffer后，暂时只使用一次，与矩阵A的一行进行点积之
后，便需要读入矩阵B的**下一列**。当矩阵A的一行消耗完之后，B之前**读过的列**又需要被读入Stream Buffer。

> 一方面，主存按行burst数据，因此取B的第一列数据时，后续X列（X=burst长度）实际上也会被访问到，而实际上后续X列的数据也确实会在第一列数据使用完后被使用，因此应该把它们缓存到Cache中。

> 另一方面，当A的一行和B的N列计算结束得到C的一行之后，需要计算C新的一行，这时候B此前访问过的列，会再次依次被访问，因此缓存在Cache中是有用的。

新增了如下设计支持上述功能：
1. `cfg-stride`指令：用来配置某个流 **某次** 向存储系统取数填充 流Buffer 时各个element的地址间隔。对于矩阵乘示例B数组，该值即为 N*4(Byte)
2. `cfg-tileStride`指令：用来配置某个流 向存储系统取数填充 流Buffer 时，**各次**取数首地址之间的地址间隔。对于矩阵乘A数组，该值即为两行的行首地址间隔（K*4）；对于B，该值为两列的列首地址间隔(4)
3. `cfg-outerIter`指令：该指令搭配`cfg-length`指令使用，当某个流burst的次数达到配置值时，若`outerIter`次数达到配置值，则该流不能再取数；否则取数首地址**回环**到最开始配置的地址，`outerIter`次数++。
4. 考虑利用Cache进行复用，Stream Buffer需要数据时直接去Cache中查找数据是否已经在Cache中，如果命中则直接由Cache提供数据；如果miss，复用Cache向主存访问数据的通路。数据取回后，将一整个Cacheline放到Cache，将流Engine需要的数据给流Engine



### 5.3 矩阵A B 流计算指令消费：icntMap更新逻辑

提要：
1. 每个流都对应一个`icntMap`，本质上就是一个计数器
2. 一条流计算指令会需要至少2个流操作数（目的操作数可以是通用寄存器）

流计算指令的指令码本身不携带 **各个流操作数 在相应流Buffer中的索引**，各操作数的索引 是指令来到dispatch级时 **各流操作数对应的icntMap** 的值。在向量加算法（A+B）中，dispatch级每fire一条流计算指令，流A和流B 相应的icntMap就会递增1，但是在矩阵乘中不是这样的。

在内积算法中，A的某一行会依次和B的N列进行点积，得到N个C的result；对于每个result，它是由A的这一行的所有element和B的相应列的所有element乘累加得到的。

这里假设流Buffer一个半区是32字（并且K=32），以C的前两行计算为例，它需要A的流Buffer的两个半区依次取好A的前两行各32个数据，并且B的各列按顺序交叠的load到两个半区中。

> 对于B，它的icntMap更新策略很简单，就是每fire一条流计算指令递增1；

> 对于A，它的icntMap更新策略是：fire一条流计算指令时，更新值与当前icntMap的值相关：从0递增到31，然后重新回到0再递增到31，重复N次。

具体的过程是这样的：

![alt text](../pic/image-gemm.png)

各条流乘法指令被分配的索引应该是这样的：

| 第 X 条 | A 索引 | B 索引 | 备注
|--------|--------|--------|--------|
| 0      | 0      | 0      | A第1行与B第1列开始计算
| 1      | 1      | 1      |
| …      | …      | …      |
| 31     | 31     | 31     |
| **`32`**     | **`0`**      | 32     | A第1行与B第2列开始计算
| 33     | 1      | 33     |
| …      | …      | …      |
| 63     | 31     | 63     |
| **`64`**     | **`0`**      | 64     | A第1行与B第3列开始计算
| …      | …      | …      |
| N×32−1 | 31     | N×32−1 |
| N×32   | **`32`**      | N×32   | **A第2行**与B第1列开始计算


需要实现2条配置指令，一条配置`i_limit`，即icntMap递增多少时会回环；一条配置`i_repeat`，即icntMap回环多少次后回环累计清0，本次不回环

### 5.4 流计算指令：新增可写通用寄存器的计算指令

此前在向量加程序中，两个流计算的结果不会作为后续计算的源操作数，因此非常适合把结果存放在流Buffer中，集中写回主存

但在矩阵乘中，对于C的每个result，它是由A某一行所有element和B相应列的所有element乘累加得到的。也就是说，流乘法指令的结果会进行复用。

考虑到通用寄存器本身就具有“复用”的特性，因此新增可写通用寄存器的流计算指令，通过funct3与原指令区分，这条指令的内联汇编如下：

```c
    static int cal_stream_rd(int fifo_id_src0,int fifo_id_src1)
    {
        int rd;
    	int rs1 = (fifo_id_src0 & 0x3) | ((fifo_id_src1 & 0x3) << 2);
        asm volatile (
           ".insn r 0x0b, 7, 0, %0, %1, x0"
                 :"=r"(rd) 
                 :"r"(rs1)
         );
        return rd; 
    }
```

矩阵乘内积算子实现如下：

```c
    for (int i = 0; i< M*N; i++){
        int sum = 0;
        for (int k = 0; k < K;k++){
            sum += cal_stream_rd(0,1);
        }
        c[i] = sum;
    }
```

## 6. FFT的流

FFT-32 的 stream 实现，是目前流引擎里最复杂的一类使用方式。它一方面继续使用 load stream 从内存搬运数据，另一方面又不再把中间结果统一写到独立的 store stream，而是把中间结果直接写回两个源 stream buffer 的另一条 line 中。

这要求硬件同时支持：

* 源操作数按普通 `iCntMap` 规则获取
* 目的操作数按 FFT 蝶形图的写回规律获取
* stage 之间在同一个 stream buffer 内完成“另一条 line 写回”
* 在最后一个 stage 把结果改为写回通用寄存器TODO:目的是预取

### 6.1 数据组织与基本思路

在 `RV-Software/cfft-4k-sh-stream/src/cfft_4k-sh-stream.c` 中，一个 stream buffer 的规模是 `2 * 32 word`，可以视为两条 line：

* `line0`
* `line1`

由于一个复数点占两个 word，因此每个 buffer 恰好可以放下 16 个复数点，两路 buffer 拼起来正好覆盖 32 点 FFT 的一整个 block。

32 点 FFT 在 4K FFT 的 block 版本中会被外层循环调用 128 次。对每个 block：

1. 先把当前 block 的前 16 个复数点加载到流 0
2. 再把后 16 个复数点加载到流 1
3. 之后执行 Stockham 蝶形计算

Stockham 形式的好处是每个 stage 都从 `src` 读、向 `dst` 写；映射到 stream buffer 后，`dst` 不再是单独的数组，而是两个 stream buffer 当前 block 的另一条 line。

### 6.2 软件侧从普通 FFT 到 stream FFT 的变化

普通 32 点 FFT 的核心循环是：

```c
for (int q = 0; q < s; q++) {
    complex_t a = src[q + s * (p + 0)];
    complex_t b = src[q + s * (p + m)];

    complex_add(a, b, &dst[q + s * (2 * p + 0)]);
    complex_t t;
    complex_subtract(a, b, &t);
    complex_multiply(t, wp, &dst[q + s * (2 * p + 1)]);
}
```

stream 化后的核心变成：

```c
for (int q = 0; q < s; q++) {
    complex_add_stream();
    complex_t t;
    complex_subtract_stream(&t);
    complex_multiply_stream(t, wp);
}
```

这里三条 stream 计算指令分别对应：

* `complex_add_stream()`：两条 `CALSTREAMPP`
* `complex_subtract_stream()`：两条 `CALSTREAMRD(sub)`
* `complex_multiply_stream()`：乘法后两条 `CALRJRKSTREAMPP`

从数据流角度看，它们正好对应蝶形中的三类结果：

* 加法结果直接写回 PP buffer
* 减法结果先写回寄存器，作为后续乘法输入
* 乘法结果再写回 PP buffer

### 6.3 为什么 FFT-32 需要新的写回索引逻辑

向量加和矩阵乘中，写回位置都比较规整：

* 要么写普通 store stream
* 要么写通用寄存器

但 FFT-32 不一样。Stockham 每个 stage 的输出位置都在变化，而且要求：

* 同一 stage 的结果写到当前 buffer 的另一条 line
* stage 切换后，新的读写位置要整体重排
* block 切换后，又要重新回到下一 buffer 的起始位置

因此不能再用原先“目的索引线性递增、到界回环”的方法描述写回位置，而需要专门为 PP 写回建立一套状态机。

在 `Stream.scala` 中，这部分由 `updatePPState()` 完成。它跟踪：

* `ppCnt`
* `ppStride`
* `ppLimit`
* `ppStage`

并结合：

* `ppBaseCfg`
* `stageLimitCfg`

为 dispatch 宽度中的每条 `CALSTREAMPP / CALRJRKSTREAMPP` 分配准确的写回位置。

其中：

* Even 路径对应 `CALSTREAMPP`
* Odd 路径对应 `CALRJRKSTREAMPP`

两条路径写回的是同一个“逻辑 dst 数组”的不同奇偶位置，所以硬件里分成了两套独立状态来生成索引。

### 6.4 PP 写回在流水线中的配合关系

FFT-32 相关的指令链路可以概括为：

1. `Decoder.scala` 识别出 `CALSTREAMPP` 或 `CALRJRKSTREAMPP`
2. `Dispatch.scala` 根据指令类型，从普通目的索引或 PP 目的索引中选择一套 `iterCnt(2)`
3. `Issue` 检查该 PP 写回位置是否为空
4. `Execute / Writeback` 将结果直接写回某个 load buffer 位置
5. `Commit` 更新 `archPP`
6. `Flush` 时用 `archPP` 恢复 `specPP`

这样处理之后，FFT-32 的中间结果就能像软件里的 `dst` 数组那样，在 stage 之间连续流动，而不需要额外引入第三个中间结果 buffer。

### 6.5 最后一个 stage 的特殊性

前面的 stage 中，蝶形计算结果都还会被后续 stage 继续消费，因此适合继续写回 PP buffer。

但最后一个 stage 不同，它的结果已经是最终 FFT 输出，因此 `fft_32_stockham_stream()` 中改成：

* `complex_add_stream_last()`：通过 `CALSTREAMRD(add)` 把结果写回通用寄存器
* `complex_subtract_stream()`：通过 `CALSTREAMRD(sub)` 获得中间寄存器结果
* `complex_multiply()`：在寄存器里完成乘法后，直接写内存数组

这样做之后，stream buffer 中会有一条 line 被腾空，硬件就可以在这条 line 上异步发起下一 block 的取数请求，实现 block 间重叠。

### 6.6 FFT-32 对访存路径的影响

FFT-32 不只是改了写回索引，也对 block 间切换时的取数控制提出了新要求。

在当前实现中，当一个 block 的 PP 写回完成到特定阶段后，硬件会通过 `tagR` 等状态触发对：

* `oIterCntMap`
* `addrDyn`
* `burstCntMap`
* `lengthMap`

的额外调整，用于“解禁”下一 block 的取数。这部分逻辑位于 `Stream.scala` 的访存部分，核心目的就是让 FFT 的 block 级推进与 PP 写回推进保持一致。

从软件角度看，程序仍然只是先配置一次 stream，再在外层循环中不断执行 FFT kernel；但从硬件角度看，block 之间何时允许继续 load，已经不再只是简单地看 line 是否空闲，还要看 PP 写回状态是否推进到了可以切 block 的位置。

## 7. 软件配置流与 stream kernel

这一节结合当前仓库中的三个程序，说明软件如何配置 stream，以及 kernel 中的流计算指令如何与硬件配置对应起来。

### 7.1 配置指令的基本含义

当前软件里常用的配置与计算指令如下：

* `cfg_i(outerIter, length, fifo_id)`
  配置该流的 block / tile 规模。`length` 决定一轮共要取多少 word，`outerIter` 决定该模式要重复多少轮。

* `cfg_i_limit(limit, fifo_id)`
  配置索引区间长度。

* `cfg_i_repeat(repeat, fifo_id)`
  配置同一索引区间重复次数。

* `cfg_reuse(reuse, fifo_id)`
  配置读入 stream buffer 后，每个元素可以被消费多少次；对应硬件 `readyMap` 的初值。

* `cfg_stride(stride, fifo_id)`
  配置一次取数过程中，相邻 word 的地址间隔。

* `cfg_tilestride(tilestride, fifo_id)`
  配置相邻两次 tile 取数的起始地址间隔。

* `cfg_load / cfg_axi_load(addr, fifo_id)`
  配置该流从哪个起始地址取数，以及走 L2 还是 AXI 路径。

* `cfg_store(addr, fifo_id)`
  配置普通 store stream 的写回地址。

* `cal_stream(src0, src1, dst)`
  流流流，结果写普通 store stream。

* `cal_stream_rd(src0, src1)`
  流流寄，结果写通用寄存器。

* `cal_stream_pp(...)`、`cal_rjrk_stream_pp(...)`
  结果写 PP buffer，主要用于 FFT-32。

下面分别看三个程序。

### 7.2 向量加：最基本的线性流

`RV-Software/stream-test/src/stream-add.c` 展示的是最简单的一类用法：

```c
cfg_i(1,512,0);
cfg_i(1,512,1);
cfg_i(1,512,2);
cfg_reuse(1,0);
cfg_reuse(1,1);
cfg_i_limit(512,0);
cfg_i_limit(512,1);
cfg_i_limit(512,2);
cfg_i_repeat(1,0);
cfg_i_repeat(1,1);
cfg_i_repeat(1,2);
cfg_stride(4,0);
cfg_stride(4,1);
cfg_tilestride(128,0);
cfg_tilestride(128,1);
cfg_axi_load((uint32_t)a,0);
cfg_axi_load((uint32_t)b,1);
cfg_store((uint32_t)c,2);
```

这一组配置的含义是：

* 0、1 号流分别顺序读取 `a` 和 `b`
* 2 号流顺序写回 `c`
* 每个元素只消费一次，因此 `reuse = 1`
* 索引不需要区间内重复，因此 `i_repeat = 1`
* `stride = 4` 表示按 word 顺序取数

对应的 kernel 也非常直接：

```c
for (int i = 0; i < 512; i++) {
    cal_stream(0, 1, 2);
}
```

也就是说，软件做的事情就是：

1. 配置三条流的访存方式
2. 配置三条流的索引推进方式
3. 在 kernel 里不断发出流计算指令

至于每次该取 buffer 的哪个位置、该不该 stall、什么时候重新发起 load/store，都交给硬件处理。

### 7.3 矩阵乘：复用 + 非连续访存 + 写寄存器

`RV-Software/stream-matrix/src/stream-matrix.c` 展示了第二类用法，即矩阵内积。

核心配置如下：

```c
cfg_i(1, M*K, 0);
cfg_i(M, K*N, 1);
cfg_i_limit(K, 0);
cfg_i_limit(M*N*K, 1);
cfg_i_repeat(N, 0);
cfg_i_repeat(1, 1);
cfg_reuse(N, 0);
cfg_reuse(1, 1);
cfg_stride(4, 0);
cfg_stride(N*4, 1);
cfg_tilestride(K*4, 0);
cfg_tilestride(4, 1);
cfg_axi_load((uint32_t)a, 0);
cfg_load((uint32_t)b, 1);
```

与向量加相比，这里出现了三个关键变化：

* A 流需要复用，因此 `cfg_reuse(N, 0)`
* A 流需要在同一段 `0..K-1` 内重复访问 N 次，因此 `cfg_i_limit(K, 0)` 与 `cfg_i_repeat(N, 0)`
* B 流按列访问，因此 `cfg_stride(N*4, 1)`，相邻两列起点用 `cfg_tilestride(4, 1)` 推进

对应 kernel 是：

```c
for (int i = 0; i < M*N; i++) {
    int sum = 0;
    for (int k = 0; k < K; k++) {
        sum += cal_stream_rd(0, 1);
    }
    c[i] = sum;
}
```

这说明矩阵乘里的流乘法结果不会马上丢弃，而是需要先在寄存器里累加，所以目的操作数不再是 store stream，而是通用寄存器。

### 7.4 FFT-32：PP 写回 + block 级重叠

`RV-Software/cfft-4k-sh-stream/src/cfft_4k-sh-stream.c` 展示了第三类用法，也是当前最复杂的一类。

初始化配置如下：

```c
cfg_i(1,32,0);
cfg_i(1,32,1);
cfg_i_limit(2,0);
cfg_i_limit(2,1);
cfg_i_repeat(2,0);
cfg_i_repeat(2,1);
cfg_reuse(2,0);
cfg_reuse(2,1);
cfg_stride(4,0);
cfg_stride(4,1);
cfg_tilestride(2*l2LineByte,0);
cfg_tilestride(2*l2LineByte,1);
cfg_load((uint32_t)temp,0);
cfg_load((uint32_t)&temp[0][16],1);
```

这里的配置可以这样理解：

* 两条 load stream 分别对应一个 32 点 block 的前 16 个复数和后 16 个复数
* `cfg_reuse(2, fifo)` 表示一个位置会先被加法消费一次、再被减法消费一次
* `cfg_i_limit(2)` 与 `cfg_i_repeat(2)` 对应的是蝶形里“加两次 / 减两次”的基本节拍
* `cfg_tilestride(2*l2LineByte)` 表示 block 间推进时跨过两个 cache line 规模的数据

对应 kernel `fft_32_stockham_stream()` 的特点是：

* 前 `LOG2_FFT_32 - 1` 个 stage 里，中间结果都继续写回 stream buffer
* 最后一个 stage 把结果转为写寄存器 / 写内存

它与普通软件版 FFT 的一个直观对比如下：

* 普通实现：`dst[...] = ...`
* stream 实现：把 `dst` 的概念映射成“PP 写回到另一条 line”

因此软件虽然没有显式维护 `dst` 数组，但实际上还是在做同样的事情，只是把这个中间结果数组隐含到了 stream buffer 里。

### 7.5 这一套软件接口和硬件之间的分工

把三个例子放在一起，可以看到软件和硬件的分工边界很清楚：

软件负责：

* 描述数据如何从内存进入 stream
* 描述索引如何推进、是否重复、是否复用
* 在 kernel 中给出计算图本身

硬件负责：

* 在 dispatch 阶段为每条流计算指令分配正确索引
* 在 issue 阶段检查源、目的位置是否 ready
* 在 execute / writeback 阶段完成 buffer 读写与 readyMap 更新
* 在访存侧根据 buffer 空闲情况、配置和动态状态发起下一轮 load/store
* 在 commit / flush 阶段维护索引状态恢复

换句话说，软件“声明模式”，硬件“执行模式”。向量加、矩阵乘、FFT-32 三个例子只是模式复杂度逐步增加，但整体使用范式是一致的。

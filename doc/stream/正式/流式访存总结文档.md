# 流式访存与计算实现总结

更新：2026-09-29。本文依据已验证的服务器代码，而不是早期接口草案。
代码基线：主仓库 `366f5e71`、RV-Software `bf9e58df`、ZirconSim `6a21bcfc`。
后续若实现变化，以实际译码、公共头和 RTL 为准。

主要入口：[Stream.scala](../../../src/main/scala/Backend/Stream.scala)、[StreamOuter.scala](../../../src/main/scala/Backend/StreamOuter.scala)、[公共头 stream_instr.h](../../../RV-Software/base-port/base/include/stream_instr.h)。
完整编码与示例索引见 [Stream-SIMD 指令集](Stream-SIMD指令集.md)，地址配置详见 [N-D 流式地址配置](N-D流式地址配置.md)。

## 1. 整体模型

Stream Engine 把访存地址生成、操作数缓存与计算指令解耦：后台按描述符取数，计算指令按当前索引消费数据，输出流在数据就绪后异步写回。

```text
AXI / L2 -> FIFO0、FIFO1 -> 标量 / SIMD 计算 -> FIFO2 -> AXI
                              |      ^
                              v      |
                             X / Y

AXI -> FIFO3 -> L2                  外积计算 <-> VReg -> FIFO2 / X / Y
```

当前固定 6 个 stream buffer，每个是 64 x 32-bit 寄存器数组，分成两个 32-word 段。
一个段为 128B，与当前 stream burst 的 32 个 word 对应；不是一个完整矩阵 tile。
这些是带索引、就绪计数与背压的 operand buffer，不是多 bank SRAM 或软件管理的大容量 scratchpad。

| ID | 名称 | 数据来源 | 数据去向 | 索引特点 |
| --- | --- | --- | --- | --- |
| 0、1 | load stream | AXI 或 L2；另有原 FFT PP 路径 | 计算指令 | 计算读索引与后台 refill 进度分开 |
| 2 | store stream | 计算结果或 VReg 导出 | AXI，完整 32-word line | 生产索引与后台 store 进度分开 |
| 3 | layout stream | AXI load | L2 word store | 独立 load/store 地址描述符，不作为 ALU 源 |
| 4、5 | X、Y | 计算结果或 VReg 导出 | 后续计算指令 | 各自独立的计算读、计算写索引；没有访存接口 |

外积另有 8 bank x 8 lane x 32-bit 的 VReg 累加器，分别保存推测态与提交态。VReg 不是 stream ID 6/7，也不是 X/Y 的别名。

## 2. 三种不同的进度

不要把下列三者混为一个计数器：

1. **地址进度**：下一次从内存的哪个地址搬入或写出，由 N-D 描述符和访存计数器决定。
2. **计算索引**：下一条指令在 buffer 中读/写哪里，由 `cfg_i_limit/repeat/offset` 决定。
3. **剩余使用次数**：某个 word 还能消费多少次，由 `cfg_reuse` 和 ready map 维护，决定是否就绪、何时允许覆盖。

例如外积 B 的同一个 8-word 窗口用于 8 条 OMAC：`limit=8, repeat=8, offset=0` 决定保持窗口，`reuse=8` 决定每项有 8 次消费额度。只配置 reuse 不会自动让索引停住。

### 2.1 计算索引推进

`StreamIndex.advance` 用 `iCnt`、动态边界 `iLimit`、已重复次数 `iRepeat`，以及静态配置 `L/R/O` 更新状态。
每条指令先确定窗口，再按消费宽度 `w` 推进。伪代码与当前实现对应：

```text
sum = iCnt + w
if sum < iLimit:
    iCnt = sum
else if iRepeat + 1 == R:
    iCnt = sum
    iLimit += L
    iRepeat = 0
else:
    iCnt = sum - L + O
    iLimit += O
    iRepeat += 1
```

索引按 word 计，物理 buffer 下标取模 64。标量通常 `w=1`，向量通常 `w=8`；OMAC 的 A 为 1、B 为 8。
两个源 ID 相同，只消费窗口的并集：向量为 8，不是 16；OMAC 为 8，不是 9。

向量窗口可跨 32-word 段与 64-word 环形边界，但窗口内部不会执行 limit/repeat 的跳转。软件必须让一个窗口处于一次逻辑迭代内，不能把中途应回绕的 8 次标量访问直接替换成一条向量指令。

Dispatch 维护 `specI`，Commit 维护 `archI`；同拍多个槽位按程序序逐条推进，后者看到前者更新后的状态，而不是拍末一次性加指令数。
X/Y 另有独立写索引，防止生产者和消费者互相推进同一游标；两套游标仍使用该流的 limit/repeat/offset 配置。

### 2.2 配置与启动

`cfg_i` 保留原 length/outer 参数及计算索引初始化；它没有被 N-D 指令整体替代。
通常先配置计算索引和 reuse，再配完整 N-D 描述符，最后执行 load/store 地址配置启动对应通路。
`cfg_i` 会设置默认 dim1/dim2 size，因此显式 N-D size 应在它之后写。

CFG 在 MDU 顺序执行，但这不表示可以任意改写仍在后台运行的地址描述符。
普通 load 流使用当前配置，FIFO3 则在 load/store 启动时分别快照配置，二者不能套用同一重配置规则。
更精确的重置范围见 [N-D 文档](N-D流式地址配置.md)。

`cfg_reuse_empty()` 是原 FIR 的特殊兼容指令：设置待清除标记，达到 FIFO1 的指定重复阶段后清理其一部分旧 credit；无 GPR 源操作数。它不是所有流的立即清空指令，也不是通用 fence。

## 3. 四维地址与 load

固定四维，dim0 大小固定 32，只配置 stride；dim1..3 各有 size 和 stride，stride 单位为字节：

```text
addr = base + c0*T0 + c1*T1 + c2*T2 + c3*T3
```

dim0 最快，完成一条 line 后 dim1 向 dim3 逐级进位。不使用的高维设 size=1、stride=0。
这使矩阵跨列、跨行、跨 K block 的地址序列可以一次配置，不必在 K 分块循环中重新启动流。

选择 AXI/L2 是软件的显式决定：

- `cfg_axi_load` 发出 32-word 连续 AXI burst，软件需保证 dim0 stride=4，并保证 burst 不跨 4KB 边界；高维是否连续不影响选择。
- `cfg_load` 走 L2 word 请求，可以按 dim0 stride 做列访问。
- 没有“根据四维连续性自动选择 AXI”的逻辑，也没有通用 burst 边界拆分器。

AXI 收到最后一个 R beat 后推进 line；L2 发出一条 line 的最后一个请求后推进请求侧进度，返回数据另行写入 buffer。
refill 还要等目标 32-word 段允许覆盖，不能只看地址计数器。

## 4. 计算数据通路

现有标量 SSS/SSR 与 FFT PP 保留，新增 SIMD 固定 8 lane、每项 32 bit：

| 操作 | 结果去向 | 含义 |
| --- | --- | --- |
| VADD8 / VSUB8 / VMUL8 | FIFO2 或 X/Y | 两个连续 8-word 窗口逐项计算 |
| VDOT8 | 真实 GPR | 8 个乘积横向相加，不读取旧 rd；长内积用普通 CPU 加法累加 |
| VOMAC8 | 一个 VReg bank | A 的一个数广播乘 B 的 8 个数，再逐 lane 累加 |
| VCLR | 全部 VReg bank | 清零累加器，不修改 stream 索引 |
| VREGOUT8 | FIFO2 或 X/Y | 导出一个 bank 的 8 项，不清零 bank |

所有新运算按模 2^32 处理，无浮点、饱和、掩码或不足 8 项的尾部指令。
计算源 ID 直接编码在指令字段中，不通过 GPR 的值指定；但 SSR 的 rd、原 RRS 的 rs1/rs2 和 CFG 的参数仍是真实 GPR。不能把所有寄存器形状的字段一律改成 stream ID。

乘法通路共用 8 个乘法器，lane0 复用原标量乘法器；8 个加法器用于逐项加减、外积累加，或将其中 7 个连接成三层 DOT 归约树。
普通向量运算和 VDOT 不修改 VReg。功能仿真已验证，尚无本版本综合面积或 Fmax 结论。

## 5. Ready、预留与提交

load-ready 保存每项剩余消费次数；store-ready 表示该项已生产、可以送往输出接口。
X/Y 同时需要生产和消费状态，不能在写入之前允许消费者读取，也不能覆盖仍有消费者需要的项。

新增向量路径分三个阶段：

1. issue 检查整个源窗口就绪，并预留/扣减执行侧消费额度；有目的流时，同时预留目的窗口。
2. execute 读取窗口并计算，结果随指令保存；不让未提交的向量结果触发 FIFO2 store。
3. commit 更新提交侧消费状态，将逐元素结果或 VReg 导出值写入目的 FIFO/ready map。

load refill 需同时检查执行侧与提交侧的整段剩余次数，避免尚未提交的读取让旧数据提前被覆盖，导致 flush 后无法重执行。
VReg 在执行时更新推测态、提交时更新提交态，flush 恢复已提交前缀；导出值保存在 ROB 中，后续 VCLR/OMAC 不会改变较早导出指令的结果。

以上是新增向量路径的规则。旧标量 SSS/PP 仍保留原 WB 处理，不应据此声称所有历史配置、标量副作用都具有完全相同的提交隔离能力。

## 6. 内存一致性与同步

当前 L1 写直达、L2 写回且写分配；stream 的直接 AXI 路径绕过 L2。
CPU 初始化或 pack 后的数据可能还在 L2 脏行里。因此新 SIMD 测试的两路输入都选 `cfg_load`，不能用一个 fence 把脏行自动变成 AXI 内存数据。

FIFO2 仍按完整 32-word line 写 AXI，暂不是任意 N-D store。
单个 W beat 握手后可释放对应 buffer 项；但完成通知必须等 AXI B 响应，不能把最后一个 W 当成整笔事务完成。
`AXIArbiter.writePending` 覆盖 AW/W/B 阶段，B 握手后才清除。

`stream_fence()` 发出标准 `fence rw,rw`：前端单独分发，等待较早 ROB 指令、CPU store buffer 和当前 stream 排空条件，再放行后继指令。
FIFO2 的排空条件包含上述 B 响应等待，测试在读取 AXI 输出之前使用它。

边界必须保留：

- fence 不做 cache flush/invalidate。直接 AXI 输出地址在写回前不能已有会干扰它的 CPU cached 数据；当前测试采用 128B 对齐、CPU 不提前访问的输出区。
- 不足 32 words 的 FIFO2 尾段不能靠 fence 强行写出，可能一直等不到排空。
- **当前 fence 不是 FIFO3 整个转置任务的完成通知。** 排空条件检查 FIFO3 ready、在写 line 和待响应请求，却没有包含整个 load 描述符的完成状态；line 间的空隙可能暂时满足条件。现有转置程序仍使用固定等待后检查结果，不能拿 SIMD FIFO2 的 fence 测试替它证明同步完备。

## 7. FIFO3 转置

FIFO3 由 AXI load 生产数据并拉高 ready；原来 store-ready 的生产者由计算指令换成了 load 返回。
一条 32-word line 就绪后，按独立目标地址序列向 L2 发 word store，不必先持有完整 32x32 tile，也不需要在 buffer 内交换元素。

32x32 转置示例：

```text
load:  src + row*128 + col*4       # 每行连续 AXI 读取
store: dst + col*128 + row*4       # 同一批数据逐项写目标列地址
```

L2 接受一个写请求后即可推进下一项；响应使用 pending 计数跟踪，不再逐项等响应才发下一个请求。
STE 的 L2 写请求与 load 请求共享端口并接受背压；FIFO2 写 AXI、FIFO3 写 L2，不需要两路 stream AXI store 仲裁，但不代表 L2 没有共享资源竞争。

测试 src/dst 显式 128B 对齐。4KB 的目标矩阵因此覆盖 32 条 L2 line；冷缓存下写分配可能引发 32 次 refill，但具体事件与周期仍取决于初始缓存状态。
L2 仍是写回 cache。仿真将实际 L2 直写事件反映到 reference memory，是为了后续 CPU load 的 difftest 一致，不是让物理 L2 变成写直达，也不能单独证明转置地址正确。最终独立软件 golden 才检查矩阵关系。

细节和既有 profile 记录见 [Layout Transform 修改说明](Layout-Transform修改说明.md)。

## 9. 测试入口与证据

在主仓库运行：

```sh
sbt --batch 'testOnly StreamSimdTest StreamOuterTest StreamFenceTest'
bash tests/stream-outer/run.sh
```

也可在程序目录用 `make NAMES=stream-simd-matrix run` 等方式单独运行。已有匹配的模拟器时，批量脚本可用 `SKIP_BUILD=1`，具体参数见 [run.sh](../../../tests/stream-outer/run.sh)。

2026-09-29 的功能验证覆盖上述 SIMD 新程序与原有回归，共 13 个程序最终均通过；3 个 Chisel suite 共 8 项通过。
矩阵首次运行因 C golden 太慢被主动中止，调整 golden 的遍历顺序后重跑通过；不是第一轮批量退出码为成功。
详见 [SIMD8 实现与测试记录](../simd8-implementation-20260929.md) 和 [外积合入记录](../outer-merge-20260929.md)。

这里不报告新的性能加速比。包括初始化、pack、golden 的整程序 cycle 不能直接当作 kernel 时间；旧 profile 数据也不能自动代表本次 SIMD 版本。

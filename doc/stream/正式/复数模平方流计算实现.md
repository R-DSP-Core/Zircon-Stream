# 复数模平方流计算实现

## 1. 目标

目标计算为：

```c
for (int r = 0; r < R; r++) {
    for (int d = 0; d < D; d++) {
        uint32_t acc = 0;
        for (int a = 0; a < A; a++) {
            acc += re[r][d][a] * re[r][d][a]
                 + im[r][d][a] * im[r][d][a];
        }
        heatmap[r][d] = acc;
    }
}
```

当前测试规模为：

```text
R = 64
D = 32
A = 4
输入复数数量 = R * D * A = 8192
输出数量 = R * D = 2048
```

## 2. 数据通路

当前实现使用 4 条参与计算的 stream：

| FIFO | 角色 | 数据来源/去向 |
| ---: | --- | --- |
| 0 | `re` 输入流 | AXI load |
| 1 | `im` 输入流 | AXI load |
| 4 | 中间流 X | 接收 `re * re`，不连接访存接口 |
| 5 | 中间流 Y | 接收 `im * im`，不连接访存接口 |

每个复数元素对应三条流计算指令：

```c
cal_stream_mul(0, 0, 4);       // X = re * re
cal_stream_mul(1, 1, 5);       // Y = im * im
acc += cal_stream_rd_add(4, 5); // acc += X + Y
```

前两条是 SSS 指令，结果写入计算中间流；第三条是 SSR 指令，结果写入编译器分配的通用寄存器，随后使用普通整数加法完成 `A` 维 reduction。

最终 `heatmap[r][d]` 使用普通 `sw` 写入内存。FIFO 2 仍保留为原有普通 store stream，本实现没有把 X/Y 或 reduction 结果错误地合并到 FIFO 2。

## 3. 指令编码

详细字段规则见[流计算指令编码约定](./流计算指令编码约定.md)。本功能涉及的两类指令为：

| 类型 | `rd` | `rs1` | `rs2` | `funct3` | `funct7` |
| --- | --- | --- | --- | ---: | ---: |
| SSS mul | 目的 stream ID | 源 stream ID 0 | 源 stream ID 1 | 2 | 16 |
| SSR add | 目的 GPR | 源 stream ID 0 | 源 stream ID 1 | 7 | 0 |

两个平方指令的固定编码为：

```text
cal_stream_mul(0, 0, 4) -> 0x2000220b
cal_stream_mul(1, 1, 5) -> 0x2010a28b
```

SSR 的 `rd` 由编译器分配，因此完整指令字会变化，但 `rs1=4`、`rs2=5` 保持不变。

软件宏要求直接编码的 stream ID 是数字字面量或数字 `#define`，不能使用运行时变量。CFG 指令的参数仍通过 GPR 传递，不受此限制。

## 4. X/Y 双索引

输入流 0/1 只有计算指令消费数据，因此继续使用原有的一套索引。X/Y 同时具有生产者和消费者：

```text
SSS mul -> 写 X/Y
SSR add <- 读 X/Y
```

如果生产和消费共享一套索引，写入 `X[0]` 后读操作会直接得到 `X[1]` 的索引，导致读不到刚产生的数据。因此只有 FIFO 4/5 增加第二套索引：

| 状态 | 用途 |
| --- | --- |
| `specI / archI` | X/Y 作为源操作数时的推测/提交消费索引 |
| `specComputeWriteI / archComputeWriteI` | SSS 写 X/Y 时的推测/提交生产索引 |

FIFO 0/1/2/3 不增加计算生产索引，仍保持原有单套索引语义。

索引在 Dispatch 阶段分配推测值，在 Commit 阶段推进提交值。实际访问位置为：

```text
buffer index = iterCnt % 64
```

## 5. 同源操作数去重

平方计算的两个源 ID 相同：

```c
cal_stream_mul(0, 0, 4);
```

两个 MDU 输入都读取同一个 FIFO 元素，但该元素只被消费一次。因此 Dispatch、Commit 和 readyMap 更新均按物理 stream ID 去重：

```text
src0 ID == src1 ID
    两个计算输入读取同一数据
    消费索引只推进一次
    ready 计数只减一次
```

否则会把平方错误地执行成相邻元素相乘，并使后续索引整体错位。

## 6. readyMap 与反压

FIFO 4/5 不连接 AXI 或 L2，其 ready 状态完全由计算指令维护：

1. SSS 写回 X/Y 时，将对应位置写入计算结果，并按 `reuseCfg` 设置 ready。
2. SSR 读取 X/Y 后，将对应 ready 计数减一。
3. SSS 只有在目的位置 ready 为 0 时才能发射，防止覆盖尚未消费的中间结果。
4. SSR 只有在两个源位置 ready 均非 0 时才能发射。

提交态 readyMap 按 ROB 提交顺序折叠读写事件，避免同一周期内生产和消费更新相互覆盖。

## 7. flush 周期修复

`64 x 32 x 4` 首次运行时，在完成第一组 `D=32` 后出现 stall。调试状态为：

```text
X/Y 推测读写索引 = 135
X/Y 提交读写索引 = 128
推测 ready 项数 = 1
提交态 ready 项数 = 0
```

双索引和提交态本身正确，问题来自 flush 同周期仍有错误路径的 stream WB。原先 flush 先恢复 `loadreadyMap`，随后错误路径 WB 又把某个 X/Y 位置置为 ready，覆盖了恢复结果。下一轮生产者回到该位置后便一直认为目的位置被占用。

当前在 Stream Engine 的 WB 副作用入口增加：

```scala
when(io.wb(i).wvalid && !io.cmt.flush) {
    // consume/produce stream data
}
```

这样被 flush 的指令不会继续读取、写入或修改 stream readyMap。该修复是实际循环换行时触发的功能修复，不是额外的分支预测性能测试。

## 8. 软件实现

源码位于：

```text
RV-Software/stream-test/src/stream-complex-mag.c
```

四条 stream 均配置为 8192 次线性访问：

```c
cfg_i(1, 8192, fifo_id);
cfg_i_limit(8192, fifo_id);
cfg_i_repeat(1, fifo_id);
cfg_reuse(1, fifo_id);
```

FIFO 0/1 额外配置 4B word stride，并从两个 128B 对齐的静态数组执行 AXI load。静态初始化避免 CPU 先写数组、AXI 随后绕过 cache 读取时产生一致性问题。

输入数组各为 32KB：

```text
re: 8192 * 4B = 32KB
im: 8192 * 4B = 32KB
```

输出数组为 8KB：

```text
heatmap: 2048 * 4B = 8KB
```

## 9. Difftest

ZirconSim 新增 `ComplexMagnitude` 模式，参考模型支持：

1. 跟踪 FIFO 0/1/4/5 的配置与索引。
2. 根据 FIFO 0/1 的地址配置读取参考内存。
3. 模拟 X/Y 两个 64-word 环形中间 FIFO。
4. 对 SSS add/sub/mul 生成中间流参考写回。
5. 对 SSR add/sub/mul 生成 GPR 参考结果。
6. 对相同源 ID 只推进一次参考索引。

因此本测试有两层检查：

```text
StreamDifftest
    逐条比较流计算指令的中间结果和 GPR 写回

C software golden
    计算完整 heatmap，并检查全部 2048 个最终输出
```

不是只依赖静态 golden，也不是因为 difftest 不支持新指令才做软件比较。

## 12. Profile 结果

### 12.1 Stream kernel

真正的 stream 计算主体是 Block 4：

```text
迭代次数: 2048
Block 累计 cycles: 27211
平均: 13.29 cycles/output
中位数: 12 cycles/output
P90: 12 cycles/output
超过 12 cycles 的迭代: 130，占 6.35%
平均 IPC: 1.35
```

Block 4 的墙上时间范围约为 cycle `307..28356`，共 28049 cycles。大多数输出稳定在 12 cycles，说明 X/Y 的生产、消费和 ready 反压没有形成持续瓶颈。

按当前 12-cycle 稳态计算：

```text
2048 * 12 = 24576 cycles
实际 Block cycles = 27211
长尾额外开销 = 2635 cycles
```

可以从指令数直接推导计算侧下界。总共有：

```text
R * D * A = 64 * 32 * 4 = 8192 个复数元素
每个元素 = 2 条 SSS mul + 1 条 SSR add = 3 条流计算指令
计算基线 = 8192 * 3 = 24576 cycles
```

内存侧需要独立计算。两个输入数组共包含 `64 * 32 * 4 * 2` 个 word，每个
128B burst 搬运 32 个 word；输出 heatmap 覆盖 64 条冷 cache line：

```text
输入 STREAM burst = 64 * 32 * 4 * 2 / 32 = 512 次
输出 write-allocate = 64 * 32 / 32 = 64 次
总内存事务 = 512 + 64 = 576 次
```

profile 中 512 次 STREAM 的 duration 总和为 23521 cycles，64 次 DATA
write-allocate 的 duration 总和为 2934 cycles，因此 memory 时间近似为：

```text
Tmemory = 23521 + 2934 = 26455 cycles
平均每次事务 = 26455 / 576 = 45.93 cycles
```

计算和访存是重叠的，所以 kernel 理论时间应取两者的较大值，而不是相加：

```text
Tcompute = 24576 cycles
Tmemory  = 26455 cycles
Tkernel  >= max(Tcompute, Tmemory) = 26455 cycles
```

实测 Block 4 累计 27211 cycles，墙上时间为 28049 cycles。结果接近 memory
下界，说明当前模平方已经主要受串行内存事务限制；相对 26455-cycle 下界的差值
来自事务间空隙、启动收尾和基本块外的调度周期。

### 12.2 软件 golden

Block 8 是普通 `lw/mul/add` 实现的软件 golden 与检查主体：

```text
Block 8 cycles: 71520
占总运行 cycles: 约 65%
```

因此不能使用总运行时间 `109250 cycles` 直接评价 stream kernel；总时间主要由计算结束后的 golden 校验占据。

### 12.3 AXI 输入

STREAM timeline 中共有 512 个 128B AXI burst：

```text
re: 256 bursts = 32KB
im: 256 bursts = 32KB
合计: 512 bursts = 64KB
```

平均每个事务从请求到完成约 45.94 cycles。STREAM 事件从 cycle 299 持续到 28254，与 Block 4 基本完全重叠，说明输入搬运和计算实现了流水重叠。

当前 timeline 中这些 AXI 事务彼此不重叠，表现为单 outstanding 的请求序列。

### 12.4 Heatmap write-allocate

程序执行了 2048 条 heatmap `sw`，但只产生 64 次首次写 cache line 的 write-allocate：

```text
heatmap 大小 = 2048 * 4B = 8192B
L2 cache line = 128B
cache line 数 = 8192 / 128 = 64
```

数组按 128B 对齐，因此恰好覆盖 64 条 line。每条 line 的第一条 `sw` miss 并触发 write-allocate，后续 31 条 `sw` 命中同一条 line。

把 512 个 STREAM 事务和 64 个 heatmap write-allocate 合并观察：

```text
事务数: 576
事务持续时间总和: 26455 cycles
观察窗口: 27955 cycles
请求活跃时间比例: 94.63%
重叠事务数: 0
```

这里的 94.63% 表示几乎一直存在未完成的内存事务，不等价于 AXI data beat 带宽利用率。

### 12.5 长尾规律

Block 4 的慢迭代具有固定周期：

```text
iteration % 32 == 0
    平均约 22.17 cycles，主要对应输入 line 供给边界

iteration % 32 == 4
    平均约 42.59 cycles，64 次均变慢
    与 64 次 heatmap write-allocate 一一对应

其他绝大多数迭代
    12 cycles
```

因此当前主要额外开销来自串行化的内存事务和 heatmap 写分配，而不是 X/Y 中间流本身。

## 13. 当前结论

1. 复数模平方的 SSS -> X/Y -> SSR -> GPR reduction 数据通路已经跑通。
2. X/Y 双索引和同源去重工作正确。
3. `64 x 32 x 4` 的逐指令 difftest 与全部最终输出 golden 均通过。
4. 稳态计算为 12 cycles/output，访存长尾将平均值提高到 13.29 cycles/output。
5. 后续性能优化应优先关注单 outstanding AXI 请求和 heatmap write-allocate，而不是继续增加 X/Y buffer 机制。
